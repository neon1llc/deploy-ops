# Migration from DeployGuard

The display name is **DeployOps**, the repository and command are `deploy-ops`, the package is `deploy_ops`, and environment variables use `DEPLOY_OPS_`. The proposed distribution is `neon1-deploy-ops`. Registry and trademark availability haven't been cleared.

The prior controller, policy, OIDC, Slack, cloud-federation, and split-job IaC behavior was kept and renamed. Its former CLI is now `deploy-ops gate`. The default CLI owns complete release operations. The previous 66 regression tests remain in the source tree. The MIT license notice stays in this repository, and new features use Apache-2.0 with NOTICE.

Start with a fresh state database and a new operator token. Live DeployGuard requests, leases, and grants don't migrate. To switch:

1. Export historical audit records.
2. Let active work finish.
3. Revoke old grants.
4. Replace cloud trust only after testing the new pinned workflow.

Don't copy an active lease into a renamed service or reuse old audience settings.

## Upgrading between versions

Rules that apply to every section below:

- No database schema migration, historical backfill, or automatic grant change happens unless a section says so.
- Historical records and approved bytes are never rewritten. Old evidence stays readable.
- Older writers don't enforce the newer guards. Stop them before upgrading, use one matching runtime for all writers, and keep the matching package for read-only recovery of interrupted work.
- Finish or reconcile in-flight work under its original version, then prepare fresh requests. Don't reuse an approval under a changed contract or policy.
- Back up state first.
