# Kubernetes image delivery

DeployOps updates one existing Deployment through a dedicated scoped kubeconfig. It doesn't create a cluster, namespace, Deployment, Service, RBAC binding, or admission policy. Set `context`, `namespace`, `deployment`, `container`, and an immutable `image@sha256` in the component options, and supply `DEPLOY_OPS_KUBECONFIG_FILE` outside source control, limited to this workload. The [local example](../examples/local-kubernetes/README.md) describes separate disposable prerequisites.

Preparation selects the native context once with `kubectl config view --minify --flatten --raw`. The credential-bearing result stays in process memory and anonymous native stdin. It is never written to prepared artifacts, journals, public output, or backups. Native workload commands use that snapshot through `/dev/stdin`, so a changed on-disk alias can't redirect later commands. Support needs POSIX and native HTTPS with TLS verification on. This profile doesn't alter host trust, personal configuration, or permissions.

The review binds the context, cluster label, server, namespace, Deployment, container, TLS server name, public CA digest or system-roots choice, proxy configuration digest, and client version. The context user is a label, not a verified principal. Raw proxy values and credentials aren't review data. This binds the selected client configuration, not the peer cluster, system root store, authentication plugin, or infrastructure ownership.

The Deployment must expose its UID, resource version, and selected container baseline. Before execution, the newly selected connection must match the review. One JSON Patch tests UID, resource version, container name, and previous image before replacing the image, so a recreated object with the same name, version, and image doesn't inherit old approval. Native rollout status and final UID, image, and observed-generation and replica readback are separate checks. Same-image delivery observes readiness without a patch. Nothing creates or adopts a missing object.

## Operate and recover

Run `deploy-ops run ENVIRONMENT --component COMPONENT --only` to prepare. Inspect the connection and UID in the release view or CLI status, then approve the exact digest. Waiting returns exit 3. `deploy-ops approve RELEASE COMPONENT --digest DIGEST` holds approval, and `deploy-ops resume RELEASE` is the separate execution. Compatibility failures also appear in console review, and a displayed approval doesn't override native admission checks.

The public `kubernetes-operation.json` records intent before the patch, acknowledgement separately, and bounded readback afterward. Once an operation record exists, apply refuses to resend. After a timeout, interruption, or lost response, use `deploy-ops provider inspect RELEASE COMPONENT` or **Read provider status**. Readback rechecks the connection before contacting a cluster. A changed connection returns `connection-changed` without a cluster read, and a different UID is `object-replaced`. A converged observation after a lost acknowledgement doesn't invent controller success, restore a lease, or authorize replay. Follow the [recovery workflow](workflows.md).

Coherent private backup includes the public native journal and excludes worker homes. Restored copies stay inspection-only. Deployment inspection format 2 can't represent this operation and refuses it, so use native readback or coherent backup. Older inspection formats keep their meanings. New writers refuse old Kubernetes mutation evidence before claim. See [migration](migration.md).

## Qualification

kubectl v1.36.1 ran against an owned TLS API fixture for pinned alias behavior, atomic UID refusal, and one accepted patch with a lost acknowledgement followed by read-only recovery. All fixture sockets and temporary TLS keys were removed. The first fixture omitted watch-list initial bookmarks, and the corrected one follows [Kubernetes API concepts](https://kubernetes.io/docs/reference/using-api/api-concepts/). The native selection flags follow [kubectl config view](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_config/kubectl_config_view/). No upstream implementation was copied or bundled.

These checks exercise the real client and HTTP and TLS protocol, not a Kubernetes controller, readiness probe, managed cluster, admission policy, RBAC, or workload HTTP delivery. No dedicated real cluster was available and the local Docker daemon was unavailable, so no personal context was adopted and no daemon or cluster was started. The earlier v0.7 VM workload proof is historical and doesn't qualify this contract. See [verification](verification.md).
